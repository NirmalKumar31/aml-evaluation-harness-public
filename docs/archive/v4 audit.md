# V4 publication-readiness audit

**Repository:** AML — alert-budget-aware evaluation for transaction monitoring
**Audit date:** 2026-09-14
**Audited branch:** `main`
**Audited local commit:** `830f118550a7a671025556928bbb483bca7f211a`
**Observed `origin/main`:** `eef21c28fde99a6266fe23a1c3a40650bc36135c`
**Scope:** repository content, claims, results, methods, reproducibility, tests, packaging, dependencies, security, licensing, GitHub presentation, CI/CD, containers, Azure infrastructure, live-cloud/documentation consistency, and release hygiene.

## Verdict

**Do not publish this snapshot yet.**

The project is technically interesting and, in several respects, unusually transparent. It has a real alert-budget framing, large-scale experimental evidence, replayable metric bundles, explicit limitations, a functioning demo, a substantial test suite, pinned Python wheels for Linux, and evidence from a genuine 179.7-million-row Azure run. Those strengths can make this a strong public portfolio and research-engineering repository.

However, the present repository is **not a release candidate**. The current worktree is dirty, local `main` is ahead of the remote, the current test suite is red, most derived artifacts cannot substantiate the generator provenance they claim, the dataset pin has silently lost one of the six advertised source files, several current-facing documents contradict the corrected results, and the documented cloud reproduction commands do not satisfy the scripts' own required inputs. The publication gates currently return green despite some of these defects, so their green status is not sufficient evidence of release readiness.

This is not a cosmetic finding. A reader following the repository today can encounter mutually incompatible numbers, an invalid provenance chain, a data-verification command that declares an incomplete pin complete, and a cloud runbook that cannot run as written.

### Release decision

| Decision | Status |
|---|---:|
| Publish the current local tree | **No** |
| Publish committed `HEAD` as-is | **No** |
| Publicize `origin/main` as the finished project | **No** |
| Project has a credible path to publication | **Yes** |
| Required effort | Focused release-hardening pass, not a redesign |

## Severity model

- **P0 — release blocker:** invalidates the release snapshot, reproducibility, a material result, security/disclosure readiness, or the ability to follow the advertised workflow.
- **P1 — important:** materially weakens correctness, credibility, maintainability, or professional presentation.
- **P2 — polish:** worthwhile before launch but not independently release-blocking.

## What changed since V3

Several V3 concerns were genuinely improved:

- A canonical-results registry now exists.
- The main HI-Large post-sort table was updated to the canonical result set.
- The cache-content-digest problem appears fixed and has mutation regression coverage.
- The split-inflation counterfactual removed the tautological label check and increased the simulation to 400 draws per seed.
- Cross-architecture language was narrowed in `HANDOFF.md` and `LIMITATIONS.md`.
- Generated coverage/build outputs are staged for removal and corresponding ignore rules are being added.
- The clean committed demo runs end to end.

But several supposed fixes are partial, uncommitted, internally inconsistent, or newly regressed. In particular, the new provenance regression test exposed a real failure, while still failing to test the recorded generator hash. The V4 findings below therefore supersede the V3 release verdict.

## P0 release blockers

### P0-1 — There is no clean, uniquely auditable release snapshot

At audit time:

- Local `main` is one commit ahead of `origin/main`.
- The worktree contains unstaged source, script, security-document, ignore-rule, and derived-result changes.
- Deletion of `.coverage` and 32 generated `build/lib/aml/**` files is staged but not committed.
- Eight derived JSON artifacts are modified.
- Eight implementation/test files are modified.
- The latest remote CI runs validate `eef21c...`, not local `HEAD` `830f118...` and not the current dirty worktree.

This produces three different candidates: remote main, committed local HEAD, and local working tree. They do not contain the same code, artifacts, or tests.

**Why it matters:** no reviewer can identify which state the claims refer to. A release/tag made from the wrong state could include generated build debris, omit intended fixes, or publish artifacts generated by code not present in that commit.

**Required change:** assemble one clean release commit, push it, run all required checks on that exact full SHA, and tag only that SHA. `git status --porcelain` must be empty before the release is created.

### P0-2 — The current test suite is red

The combined current worktree collected 315 tests and returned:

```text
1 failed, 297 passed, 17 skipped
```

The failure is:

```text
test_every_derived_artifact_names_a_generator_that_exists_at_its_commit
```

It identifies three invalid artifacts:

- `categorical_ablation_medium.json` has no `generator_script`.
- `release_facts.json` has no `generator_script`.
- `split_inflation_counterfactual.json` names `scripts/split_inflation_counterfactual.py`, which does not exist at the recorded Git-root path in its claimed commit.

A clean archive of committed `HEAD` passes its older suite:

```text
297 passed, 17 skipped
```

That is not exculpatory: the clean commit lacks the newly modified regression test and retains the invalid artifacts. It is a green older test set, not a green current release.

**Required change:** fix the artifacts/provenance model, retain and strengthen the regression test, commit everything, and obtain zero failures from a clean clone of the exact proposed release SHA.

### P0-3 — Derived-artifact provenance is mostly unverifiable or false

I independently compared every derived artifact's recorded generator path/hash against the generator file as it existed at the artifact's recorded Git commit. Of ten artifacts, only two currently establish the claimed relationship.

| Artifact | Result | Problem |
|---|---|---|
| `categorical_ablation.json` | Match | Generator exists and hash matches |
| `typology_null.json` | Match | Generator exists and hash matches |
| `categorical_ablation_medium.json` | Invalid | No generator script recorded |
| `release_facts.json` | Invalid | No generator script recorded |
| `split_inflation_counterfactual.json` | Invalid | Recorded path is absent at claimed commit |
| `cost.json` | Invalid | Recorded generator hash does not match generator at claimed commit |
| `dataset_facts.json` | Invalid | Recorded generator hash does not match generator at claimed commit |
| `dataset_pin.json` | Invalid | Recorded generator hash does not match generator at claimed commit |
| `sbom.cdx.json` | Invalid | Recorded generator hash does not match generator at claimed commit |
| `split_inflation.json` | Invalid | Recorded generator hash does not match generator at claimed commit |

The five hash mismatches appear to record current uncommitted generator bytes while claiming the current committed Git SHA. This is exactly the state provenance metadata is supposed to prevent.

The new regression test checks only that `git cat-file -e <sha>:<script>` succeeds. Despite its intent, it does **not** compare `generator_sha256` with the bytes at that commit, so all five hash mismatches escape it.

The current helper also records `git_sha()` when the tree is dirty without recording `dirty: true`. It does not capture input hashes, parameters, environment/lock identity, or output hash. A commit ID alone cannot identify an uncommitted generator.

**Required change:**

1. Commit generator code first.
2. Regenerate artifacts from a clean checkout of that commit.
3. Commit artifacts separately.
4. Record the full code SHA, repository-root-relative generator path, generator SHA-256, `dirty: false`, input identities/hashes, parameters, dependency/environment identity, and output hash.
5. Make the test recompute every recorded hash from Git objects and fail on missing fields, a dirty generation state, an abbreviated/unknown SHA, or a missing input.

Do not regenerate artifacts from dirty code and label them with the last committed SHA.

### P0-4 — Dataset verification can silently redefine an incomplete dataset as complete

The current modified `dataset_pin.json` contains five files, not the six described by the project. It has silently dropped:

```text
HI-Large_Trans.csv
```

The prior committed pin contained this file. The regression is caused by pin generation using only files present locally. After truncation, both the default verification and `--require all` report five checked and zero missing, because “all” means all entries remaining in the already-truncated pin—not the project's canonical six-file dataset contract.

`DATA_LICENSE.md` still states that all six files are recorded. That is false for the current working artifact.

**Why it matters:** an incomplete local dataset can overwrite the pin, after which verification blesses the incomplete set. This compromises input identity for the most important 179.7M-row result.

**Required change:**

- Define the canonical six filenames in a schema/manifest independent of the mutable pin.
- Make `--require all` assert exact set equality against that manifest.
- Make pin generation refuse missing expected inputs unless an explicit, reviewed migration flag is supplied.
- Restore the validated HI-Large transaction hash and size from a trusted source.
- Add tests proving a five-file pin cannot pass “all” and cannot overwrite a six-file pin silently.

### P0-5 — The documentation still presents contradictory scientific results

The canonical HI-Large post-sort results are now approximately:

- Recall@200 mean: `0.08785`
- Precision@50 mean: `0.42887`
- Ring recall: `0.86876`
- Null ring recall: `0.91492`
- Lift: `0.9497`

The main result table reflects these values, but current-facing narrative still mixes the superseded unsorted lineage:

- `README.md` reports ring recall around `0.874` and lift around `0.945`.
- `HANDOFF.md` repeats `0.945` and cites `large_eval3_lgbm_s*`, which the canonical registry identifies as superseded.
- `paper/RESULTS_hi_large.md` still says Recall@200 is about `0.092` and lift is `0.945` in narrative text despite its corrected table.
- The paper still calls the benchmark “near-saturated,” even though the limitations record says that language was removed from current documents.

Other current contradictions remain:

- The README leak-placebo result uses the older global placebo figures (`±22%`, two of three caught, reversed channel not detected). The corrected stratified analysis elsewhere reports `46.1%` and says per-channel verdicts are unstable/two flipped; only the positive control is robust.
- `HANDOFF.md` says the split result is “+40%, **97% prevalence**,” contradicting its own 47%/53% decomposition and the paper. Its “not claimable” section also says 97% is prevalence.
- `HANDOFF.md` is dated 2026-09-12 and says everything was verified, although the current suite is red and artifacts changed afterward.
- `LIMITATIONS.md` first says the Medium categorical result “has not been ablated,” then later describes the ablation.
- The README claims cross-architecture “identical predictions and every derived metric.” The evidence supports identical printed metrics/order in the recorded comparison and bitwise repetition within each architecture; it does not include a cross-architecture prediction hash for the current canonical Linux result.

**Required change:** create one typed source of truth for each current claim and rewrite every current-facing occurrence from it. Retire—not merely annotate—the superseded narrative. Search current docs for the old values and result-set names, then make CI fail when a current document cites a superseded set.

### P0-6 — The publication gate produces false confidence

`make_tables.py --check` currently reports success after scanning 227 values, but 135 are exempted by `<!-- derived -->`. It has important blind spots:

- Any line containing `<!-- derived -->` is skipped in full.
- The numeric matcher largely sees only four- or five-decimal `0.xxxx` forms.
- It ignores most integers, percentages, two/three-decimal results, money, counts, durations, and scientific notation.
- It proves only token membership, not that a number is bound to the right metric, model, dataset, split, seed, alert budget, unit, or result-set version.
- Provenance checking accepts a nonempty, non-`unknown` SHA without proving that the commit exists or that generator/input hashes match it.
- Registry handling is fail-open: sources not explicitly listed as superseded are effectively treated as canonical.

This explains why stale money, percentages, test counts, marker counts, and scientific narrative all pass.

`release_facts.py --check` also reports success using a stale tracked artifact generated at `2026-09-14T04:10:30Z`, with:

- 314 tests collected
- 297 passed
- 17 skipped
- 56 result sets
- 77 derived markers
- 101 archived manifests

The current suite collects 315 and is red. CI regenerates release facts in the checkout and then checks documents, but does not assert that the committed `release_facts.json` is unchanged after regeneration. A stale tracked artifact can therefore survive a green job. Its parser also maps prose such as “314 pass” to `tests_collected`, not `tests_passed`; the prose remains semantically false because 297 passed and 17 skipped.

**Required change:**

- Replace numeric token matching with explicit claim references such as result-set ID + metric + dataset + model + seed aggregation + budget + unit.
- Require current docs to cite only allowlisted canonical result IDs; unknown should fail closed.
- Validate generated files with `git diff --exit-code` after regeneration.
- Validate exact test semantics separately: collected, passed, failed, skipped, xfailed.
- Check all displayed formats, including percentages, money, integers, durations, and rounded values.
- Narrow the marker exemption to a precise generated block with an attached source reference; never exempt an entire arbitrary line.

### P0-7 — The updated split-inflation artifact and the documents disagree

The current modified counterfactual artifact uses five seeds and 400 draws per seed. It reports approximately:

- Prevalence/composition share: mean `0.46820`, range `0.44137–0.49651`
- Detectability/score-distribution share: mean `0.53180`

Current documents still present the older 60-draw values: roughly `0.466 [0.448, 0.484]` and `0.534`, including old per-seed tables.

The updated artifact also has invalid generator-path provenance, as described in P0-3.

The interpretation remains too causal. The script resamples excluded-positive scores independently from retained positives without conditioning on day, ring, typology, account, or other selection variables. That is a useful sensitivity/composition counterfactual; it does not identify causal “effects” or prove that the residual is leakage/contamination. The preregistered HI-Medium confirmation has not been run.

**Required change:** regenerate with valid provenance, update all current documents from the final artifact, and describe this as a model-dependent decomposition/sensitivity analysis. State the exchangeability assumptions and do not label the residual “leakage” without a design that identifies leakage.

### P0-8 — The documented cloud reproduction path is not executable as written

The runbook does not satisfy required shell-script inputs:

- Provisioning requires `AML_GIT_SHA`; the documented invocation passes only `ACCT`.
- `run_cloud.sh` requires `IMAGE`; the documented invocation omits it.
- `run_hi_large.sh` requires `TAG`; the documented invocation omits it.
- The runbook says the VM verifies the source-tar SHA, but the provisioning script downloads and extracts the archive without receiving or checking a source hash.

Additional fail-open behavior:

- `run_cloud.sh` downloads Medium data only when a file is absent; it does not verify the pinned hash.
- `run_hi_large.sh` skips download for any nonempty partial file and calls that behavior resumable; it does not verify the final pin.
- Provisioning extracts into an existing `/opt/aml` without cleaning it, so deleted files can remain in the Docker build context.

**Required change:** make the exact documented commands pass shell-level contract tests, require immutable source and image identities, verify every downloaded dataset before execution, download atomically to a temporary file, and replace or clean the deployment directory before extraction.

### P0-9 — Live Azure state, cost records, and infrastructure-as-code are inconsistent

Read-only Azure inspection found:

- The experiment VM is still running.
- A public IP remains attached.
- The network security group explicitly denies inbound TCP/22 from all sources.
- The live subnet has no NAT-gateway association and does not explicitly disable default outbound access.
- The current Bicep declares a NAT gateway, no NIC public IP, no explicit security rules, and `defaultOutboundAccess: false`.
- A monthly `$60` budget exists.
- No VM auto-shutdown schedule was found.
- The resource group also retains an apparently unused container registry, disks, networking, and related resources.

The live state is therefore not reproducible from the checked-in Bicep. The VM also continues to accrue cost. The modified cost artifact estimates about `$55.66` list cost at `101.73` VM-hours, while current docs show at least three different snapshots:

- README: `$27.90`
- Runbook/Handoff: `$54.71` at `99.99` hours
- Current artifact: `$55.66` at `101.73` hours

The cost script hardcodes `actually_charged_usd: 0.0` while also saying the consumption API returned no pretax cost. Without invoice/payment evidence, this must be labeled a stated or inferred credits outcome, not measured billing fact.

**Required change:** stop/deallocate or delete resources that are no longer required; capture a final dated cost/state snapshot; reconcile live topology with IaC; add an auto-shutdown or equivalent guard if resources remain; and generate every public cost statement from one canonical snapshot. Do not expose the public IP in documentation.

### P0-10 — Replay-bundle licensing needs an explicit release decision

The replay bundles are a major reproducibility strength, but they contain row-level day, account, label, score, and ring-related transaction outputs derived from the IBM AML dataset. `DATA_LICENSE.md` correctly says that treating these as CDLA “Results” rather than redistributed data is an unreviewed interpretation.

At the same time, bundle metadata categorically states that each bundle “redistributes no part” of the dataset. That is stronger than the repository's own legal analysis supports.

**Required change:** obtain and record an explicit license/permission determination for these row-level bundles, or replace/remove fields until the public artifact is clearly within the permitted category. Align bundle notes and `DATA_LICENSE.md`. This audit does not offer a legal conclusion; it identifies an unresolved publication risk.

### P0-11 — Security reporting is not usable for a public launch

`SECURITY.md` is modified locally but still directs reporters to contact the email on the maintainer's GitHub profile. The public profile currently exposes no email. Private vulnerability reporting is not enabled. This leaves no reliable private disclosure route.

Repository-level protections are also absent at audit time:

- `main` has no protection/ruleset.
- Code scanning is not enabled.
- Secret scanning is not enabled.
- The container registry is private; unauthenticated pull fails, while public-facing instructions imply a reusable image path.

**Required change:** provide a functioning private security contact or enable GitHub private vulnerability reporting, verify it from a logged-out perspective, protect `main`, enable the available security scanners before publicity, and make image visibility/authentication instructions truthful.

## P1 important findings

### P1-1 — Several conclusions are stronger than the evidence

- “Typology ordering was refuted” is too categorical. The plug-in/model-conditional test is optimistic (`p≈0.014` in one analysis), and the qualitative ordering is unstable across two generator files. Prefer: “the preregistered ordering was not shown to be stable across the two evaluated generator files under this plug-in model.”
- “Published numbers rarely state alert budget” needs a documented literature survey or softer wording.
- “The gain is largely linear and there for the taking” is based on one logistic feature specification and overgeneralizes beyond the evaluated model/data.
- “Near-saturated benchmark” is not supported by the repository's own caveats and should be removed everywhere.
- Seeds primarily measure optimizer sensitivity on one generator draw; they are not independent dataset replicates and do not establish population-level generalization.
- The CFF phrase “the operating point practitioners care about” asserts practitioner preference without operational or survey evidence. “An operationally motivated alert-budget operating point” is supportable.

### P1-2 — The Medium categorical ablation is under-documented and under-powered

The current Medium artifact supports the narrow observation that hashed categoricals (`0.57060`) did not beat the no-categorical/one-hot result (`0.57639`) for the recorded setup. It does not support a general claim that hashing does or does not help:

- The artifact lacks valid generator provenance.
- It appears to use one seed/rung.
- Hash-collision behavior is not measured.
- `LIMITATIONS.md` contradicts itself about whether the ablation exists.

Describe this as a single-setting ablation, add collision/load diagnostics, and either repeat across the stated seed protocol or explicitly keep it exploratory.

### P1-3 — Manifest provenance is not yet archival-grade

Across the archived manifests inspected:

- 92 gold-manifest files exist.
- 45 have no `run_key`.
- 60 have no `outputs` section.
- Seven have an `unknown` code SHA.
- All are marked `status: ok`, which makes schema maturity hard to infer.

The README says every stage records inputs and checksums, but archived manifests do not consistently contain explicit per-input cryptographic hashes. Large/local cache fingerprints can use size/mtime, and outputs over 64 MB may be represented by size only. Those mechanisms may be suitable for cache invalidation, but they are not equivalent to archival provenance.

`train_matrix_sha256` hashes the feature matrix but not the ordered transaction IDs and labels that define alignment. Record separate hashes for ordered IDs, `X`, `y`, feature names/order, dtype, byte order, row count, and schema.

### P1-4 — Canonical and superseded results remain too easy to confuse

The canonical registry is a real improvement, but historical and current artifacts still sit side by side with ambiguous names such as `large_final`, `large_eval3`, and `large_lgbm`. Three older unsorted replay bundles have generic names, while newer canonical/supporting bundles use overlapping concepts.

Make status machine-readable in every artifact (`canonical`, `supporting`, `superseded`, `retracted`), use stable result IDs, put historical material under an explicit archive namespace, and make all current-doc tooling fail on noncanonical references.

### P1-5 — Replay bundles need stronger identity even apart from licensing

The bundles successfully recompute 20+ metrics exactly, which is excellent. However:

- Several use abbreviated code SHAs.
- They do not record generator script/hash and full environment/input identity.
- `source_scores` contains an absolute VM path, which is not portable and leaks implementation detail.
- They do not record a canonical dataset-manifest ID.

Use full SHAs, relative/logical source identifiers, bundle schema version, canonical dataset/result IDs, generator provenance, and file hashes for all bundle components.

### P1-6 — Test coverage is uneven in high-risk orchestration code

Current measured line coverage is about 75%, but aggregate coverage hides weak areas:

| Module | Approx. coverage |
|---|---:|
| `drift/experiment.py` | 0% |
| `demo.py` | 19% |
| `eval/run.py` | 30% |
| `models/stability.py` | 31% |
| `models/train.py` | 41% |
| `leakproof/plant.py` | 53% |
| `leakproof/sweep.py` | 58% |

These are orchestration and analysis paths where silent configuration or provenance errors matter. Add behavior-focused tests for failure handling, seed/config propagation, manifest completeness, ID/label alignment, and artifact generation. A single global percentage is not a sufficient gate; add minimums for critical packages or explicit path-based tests.

### P1-7 — Host and container validation do not test the same product

The latest remote image job reported `283 passed, 31 skipped`, while the host suite reported `297 passed, 17 skipped` for the same older remote commit. The image does not contain/mount all repository-root result artifacts, so reproducibility checks are skipped. It therefore does not prove that the released image can validate the released archive.

Define intended parity explicitly. Either build a release-validation image containing the required immutable artifacts or mount a versioned artifact package, then require the same release-critical test set in host and container environments.

### P1-8 — The demo emits non-standard JSON

The clean committed demo completes, but with bootstrap disabled it emits Python `NaN` for confidence bounds. `NaN` is not valid JSON under the standard, even though Python's parser accepts it. This conflicts with the promise of structured JSON and can break strict consumers.

Emit `null` plus an explicit reason/status, or omit unavailable bounds. Add a strict-JSON parse test using a parser/configuration that rejects non-finite values.

### P1-9 — Dependency locks are partly reproducible and partly bloated

Strengths:

- The Linux lock files contain hashes.
- A fresh dependency audit reported no known vulnerabilities.
- `pip check` passed.

Gaps:

- `requirements.lock` contains about 63 packages, including Kaggle/Jupyter/Jupytext/nbformat/bleach/Markdown tooling that appears unrelated to the production runtime.
- Local/host CI locks pin versions but are not hash-enforced in every path.
- CI upgrades `pip` to whatever is current at run time.
- `make docker-build` installs unpinned `pytest` rather than using the hashed development lock and does not supply `AML_GIT_SHA`.

Split runtime, development, research/notebook, documentation, and release tooling. Hash-lock every reproducibility-critical environment and make the supported build targets use those locks.

### P1-10 — The SBOM is not a complete release/image SBOM

The generated CycloneDX artifact describes Python lock components, but not the whole shipped container. It omits:

- OS packages
- the DuckDB Azure extension
- a complete dependency graph
- the final image digest
- build provenance tying it to an immutable source commit

Its recorded generator hash also currently mismatches its claimed commit. Generate the final SBOM from the built image, preserve the Python lock SBOM as a component if useful, attach provenance/attestation, and associate both with the release image digest.

### P1-11 — Container reproducibility and hardening are incomplete

Positive controls include a digest-pinned base image, hash-locked Linux wheels, non-root execution, read-only source intent, and managed identity. Remaining issues:

- APT package versions/repository snapshots are mutable.
- The DuckDB Azure extension is fetched without an independently recorded digest.
- Build tools and Git remain in the runtime image.
- The package is installed editable.
- Tests are shipped in the runtime-oriented image.
- The floating `latest` tag appears in operational paths.

Use a multi-stage build, install a built wheel non-editably, remove compilers/VCS from runtime, pin or verify external extension bytes, publish immutable digest-based commands, and reserve `latest` as a convenience alias only.

### P1-12 — CI coverage and tool pinning have gaps

- Bandit in CI scans `src` but not operational scripts. A fresh broader scan found no high-severity findings, but 51 medium and 10 low findings should be triaged rather than hidden by scope.
- Ruff CI omits scripts, although they currently lint clean locally.
- Actionlint is installed through a remote installer without a pinned artifact digest.
- Bicep CLI and ShellCheck are not locked to project-controlled versions in the same manner as Python dependencies.
- CodeQL/container vulnerability scanning, image signing, and a full release SBOM are absent.
- Five Dependabot action-update PRs remain open, including major updates to checkout, setup-python, Docker actions, and gitleaks.

Document accepted findings, expand source coverage, pin verification tools or run them through digest-pinned environments, review the update PRs, and establish a release security workflow.

### P1-13 — The Azure evidence is real, but the reproducibility claim needs tiers

The repository has strong evidence of a real cloud run: 179.7M rows, explicit resource/memory failures, spill behavior, managed identity, and containerized execution. But exact external reproduction depends on licensed data access, Azure permissions, mutable OS/extensions, and manual state not represented in Bicep.

Define reproducibility tiers:

1. **No-data demo:** fully public and runnable.
2. **Replay verification:** public if licensing is cleared; recomputes reported metrics.
3. **Medium raw-data run:** requires dataset access and records exact pins.
4. **HI-Large cloud run:** requires Azure/data access and immutable IaC/image/source identities.

For each tier, state prerequisites, expected runtime/cost, exact output identity, and which scientific claims it validates.

### P1-14 — Packaging is close but not release-tested end to end

The clean committed source successfully built an sdist and wheel, and the package metadata includes both code and data-license files. The package remains version `0.1.0`, with no Git tag or GitHub release. The build emitted a setuptools deprecation warning for `[tool.setuptools].license-files`, which is expected to lose support after 2027-02-18. `twine check` was not available in the project environment.

Before release:

- Move license-files configuration to the current project metadata form.
- Run `twine check` on both artifacts.
- Install the wheel into an empty environment and run CLI help plus the demo/smoke test.
- Confirm sdist/wheel contents against an allowlist.
- Derive version consistently from the release/tag or document the manual versioning process.
- Create an annotated release tag and GitHub release only after all release gates pass.

### P1-15 — The public repository configuration is incomplete

At audit time the GitHub repository is private and has:

- no topics
- no homepage
- no tag or release
- no branch ruleset
- no usable private vulnerability-reporting route
- no code/secret scanning
- no detected issue-template configuration through the API, despite a custom number-dispute template in the tree
- community-profile health around 85%; no Code of Conduct

The repository description still emphasizes “32M rows” and “one laptop,” underselling and partly misdescribing the current 180M-row/cloud story.

Configure metadata, topics, protection, issue forms, security features, release artifacts, and an accurate description before changing visibility. A Code of Conduct is optional for a personal portfolio but recommended if contributions are invited.

### P1-16 — Author identity/history exposes workstation metadata

Most commits use a local-machine identity such as:

```text
Nirmal Kumar <nirmalkumar@Nirmals-MacBook-Air.local>
```

Earlier audit prose also contains absolute workstation paths. This is not a secret, but it is avoidable personal/system metadata and looks unfinished in a public repository.

Decide deliberately whether to rewrite unpublished history to a GitHub noreply/verified address. If history is rewritten, do it once before public release and update every recorded commit reference/artifact afterward. Independently redact absolute local paths from public audit/docs and configure future Git identity.

## P2 presentation and polish

### P2-1 — The README is compelling but too defensive and historically layered

The README contains the core story, but current results, retractions, corrections, methodological caveats, and operational instructions compete for attention. A first-time reader has to reconstruct which facts are current.

A stronger front page would contain:

1. A one-sentence value proposition.
2. Status/CI/license/release badges.
3. A compact architecture/data-flow visual.
4. Three current, canonical findings with result IDs.
5. A five-minute no-data quickstart.
6. A reproducibility-tier table.
7. A concise limitations/license warning.
8. Links to methods, results, cloud runbook, and historical corrections.

Move detailed correction history to a changelog/decision record. Transparency should remain, but it should not obscure the current state.

### P2-2 — Public-facing document sprawl reduces confidence

The repository contains roughly 64 Markdown files and more than 15,000 tracked documentation lines, plus a large `Learning/` corpus. Two long LLM-council transcripts at repository root expose job-search/meta deliberation and preserve stale claims. V1/V2 are archived, while V3 remains at root and includes workstation-specific details.

Publish a deliberate document map. Move private process transcripts out of the release, convert useful decisions into concise ADRs, archive/redact audits, and clearly label `Learning/` as educational background rather than project evidence—or remove it from the distributable repository.

### P2-3 — Markdown style is not governed

A default `markdownlint-cli2` run over 64 Markdown files returned 3,148 findings, dominated by:

- 2,234 long-line findings

## Methods and scientific-quality assessment

### What is solid

- **Operational framing:** alert-budget metrics are more decision-relevant than generic ranking metrics, and the repository states budget units/ceilings in many key places.
- **Leakage awareness:** chronological/account/ring-aware splits, positive controls, placebos, and explicit retractions demonstrate serious engagement with leakage risk.
- **Replayability:** nine replay bundles allow exact recomputation of many displayed metrics without the raw licensed dataset.
- **Scale:** the repository documents a real 179.7M-row run and concrete engineering constraints rather than presenting only a toy notebook.
- **Honesty:** limitations, failed experiments, negative results, and retracted findings are preserved.
- **Engineering depth:** DuckDB-based processing, spill/memory analysis, cloud IaC, managed identity, artifact manifests, and immutable-base/container work are all useful portfolio evidence.

### What the evidence does not establish

- Independent replication across multiple raw data-generating draws.
- Operational utility in a real financial institution or with investigator feedback.
- Calibrated financial loss reduction, false-positive handling cost, or policy utility.
- Causal identification of leakage/composition effects in the split counterfactual.
- General superiority of a model family or feature family beyond the tested configurations.
- Cross-architecture bitwise identity of the current canonical predictions.
- Legal clearance to redistribute row-level replay fields.

These are not reasons to abandon the project. They are boundaries the published claims must respect.

## Writing, terminology, and formatting issues

Use these terms consistently:

- **Account-disjoint chronological split** when that is the implemented constraint; do not imply every experiment is “ring-aware” if rings are evaluated rather than used to construct the split.
- **Recall at an alert budget of N transactions** or **top-N recall**, with the unit explicit.
- **Seed sensitivity** for repeated optimization seeds on one fixed dataset/generator draw.
- **Sensitivity decomposition/counterfactual contrast**, not causal “effect,” for the current split-inflation simulation.
- **Canonical**, **supporting**, **superseded**, and **retracted** as machine-readable statuses.
- **Estimated list cost** versus **observed invoice charge**; do not conflate an asserted credit outcome with a billing measurement.
- **Bitwise repeatable within architecture** versus **same displayed metrics across architectures**.

Every headline result should name, either inline or through an unambiguous result reference:

- dataset/generator file
- row scale
- split policy
- model/configuration
- seed aggregation
- alert budget and unit
- point estimate and uncertainty definition
- canonical result ID
- code/data/environment identity

## Suggested final release gate

A single `release-check` target should fail unless all of the following are true:

1. The tree is clean and the release version/tag matches HEAD.
2. Full host tests pass with no unexpected skips.
3. Release-critical container tests match the host gate.
4. All derived artifacts reproduce from a clean checkout and remain byte-identical.
5. Every artifact's code/generator/input/output provenance validates from Git objects and declared data pins.
6. The canonical dataset manifest contains exactly the expected six inputs.
7. Current documentation contains only typed references to canonical results.
8. Generated facts/tables/costs are unchanged after regeneration.
9. Package and image artifacts pass smoke, vulnerability, SBOM, and provenance checks.
10. Security contact, legal decision, and cloud final-state attestations are present.

The gate should produce a small machine-readable release manifest containing the full Git SHA, version, test summary, package hashes, image digest, SBOM hash, canonical-result registry hash, dataset-manifest hash, documentation build hash, and audit timestamp.

## Bottom line

The repository's core idea and much of its engineering are worth publishing. The most impressive parts are the operational alert-budget viewpoint, the replayable metrics, the willingness to retract invalid findings, and the documented 179.7M-row cloud execution. The remaining problems are concentrated around **release identity, provenance enforcement, dataset-pin safety, current-document consistency, and cloud reproducibility**.

Fixing those items will do more for credibility than adding another model, experiment, or feature. Until they are fixed and verified on one clean public commit, the repository should be described as a strong work in progress—not a final reproducible release.
